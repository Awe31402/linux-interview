## 1. TRM 自己講出了答案

### 結論

整本 TRM 第 36 章，最重要的是這一句（§36.3.5，`chapter_36.txt:119`）：

> **Register File Fetch Unit** *fetch register configuration from external system memory
> through AXI interface.*
>
> （暫存器檔擷取單元，**透過 AXI 介面從外部系統記憶體抓取暫存器設定**。）

一句話，兩個重點：

1. NPU 的設定**不是 CPU 一筆一筆寫進去的**
2. NPU **自己去記憶體抓**

換句話說：

```
傳統做法                          RK3588 NPU 的做法
CPU: 寫暫存器 A = 值1             CPU: 「設定清單在 0xff800000」
CPU: 寫暫存器 B = 值2             CPU: 「開始」
CPU: 寫暫存器 C = 值3             ─────────────────────────
     ...（幾千筆）                NPU: 自己去 0xff800000 讀
CPU: 「開始」                     NPU: 自己照著設定 CNA/DPU/PPU
```

**那份「設定清單」就是被編譯過的 AI 模型。**

這不是我們推的，是 Rockchip 自己寫在手冊上的。
本章接下來要做的，只是**把那份清單挖出來看**。

## 2. 工作清單長什麼樣

### 結論

`SUBMIT` ioctl 交給驅動的，是一個 `struct rknpu_task` 陣列
（`rknpu_ioctl.h:222`）：

```c
struct rknpu_task {
	__u32 flags;
	__u32 op_idx;          /* 第幾個運算子（第幾層） */
	__u32 enable_mask;
	__u32 int_mask;        /* 中斷遮罩 */
	__u32 int_clear;
	__u32 int_status;
	__u32 regcfg_amount;   /* ← 這個 task 要寫幾筆暫存器 */
	__u32 regcfg_offset;
	__u64 regcmd_addr;     /* ← 那幾筆指令放在記憶體的哪裡 */
} __packed;
```

**只有 40 個位元組。** 而且沒有任何一個欄位跟「神經網路」有關 ——
沒有層數、沒有卷積核大小、沒有權重。

驅動看得懂的只有：**「有幾筆設定」和「設定在哪」**。

那個 `regcmd_addr` 是 [ch04](./ch04_memory.md) 講的 **IOVA** ——
NPU 眼中的位址，由 IOMMU 翻譯。

> 這就是為什麼這份驅動只有 8478 行卻能跑任何模型：
> **它根本不懂模型。** 懂模型的是 `librknnrt.so` 和編譯模型的 RKNN Toolkit。

## 3. ★ 實驗 5.1：把 regcmd 挖出來

### 結論

`regcmd_addr` 指向的內容，TRM 完全沒有描述格式。得自己挖。

### 怎麼挖

工具是 [`tools/rkspy.c`](./tools/rkspy.c)。它用 `LD_PRELOAD`
夾在 `librknnrt.so` 和核心中間，串起這條鏈：

```
攔 MEM_CREATE  → 記下每塊記憶體的 obj_addr / dma_addr / size
攔 MEM_MAP     → 記下假位移
攔 mmap/mmap64 → 用假位移綁到使用者位址
攔 SUBMIT      → 用 task_obj_addr 找出 task 陣列（它就在某塊已知記憶體裡）
                 用 regcmd_addr 落在哪塊記憶體的 dma 區間，找出 regcmd 內容
```

**完全不用改核心。** 因為 [ch04](./ch04_memory.md) 已經證明：
使用者空間也 mmap 了同一塊記憶體。**驅動看得到的，我們也看得到。**

> 🕳️ 踩過的坑：aarch64 的 glibc 走 **`mmap64`**，只攔 `mmap` 會一塊都綁不到。

### 挖出來的東西

```
--- task[0] op_idx=1 regcfg_amount=126 regcfg_offset=0 regcmd_addr=0xffc35bc0 int_mask=0x300
    regcmd buffer va=0xffff8ba4a000 dma=0xff800000 off=0x435bc0
    raw=40 10 1b 00 00 00 01 02  |u64=0x02010000001b1040| off=0x1040 val=0x0000001b tag=0x0201
    raw=04 11 00 00 00 00 01 02  |u64=0x0201000000001104| off=0x1104 val=0x00000000 tag=0x0201
    raw=00 11 00 00 00 00 01 02  |u64=0x0201000000001100| off=0x1100 val=0x00000000 tag=0x0201
    raw=0c 10 00 a0 00 60 01 02  |u64=0x02016000a000100c| off=0x100c val=0x6000a000 tag=0x0201
    raw=04 40 0e 00 00 00 01 10  |u64=0x10010000000e4004| off=0x4004 val=0x0000000e tag=0x1001
    raw=04 50 0e 00 00 00 01 20  |u64=0x20010000000e5004| off=0x5004 val=0x0000000e tag=0x2001
    raw=10 10 30 06 00 00 01 02  |u64=0x0201000006301010| off=0x1010 val=0x00000630 tag=0x0201
    raw=20 10 63 00 e0 00 01 02  |u64=0x020100e000631020| off=0x1020 val=0x00e00063 tag=0x0201
```

### 解出來的格式

一開始我把它當成「(暫存器, 值) 成對的 32 位元」，**解錯了** ——
因為右邊那欄一直重複 `0x02010000`，太可疑。

改成**每筆 8 位元組當一個 64 位元整數**來看，就通了：

```
 63 .......... 48 │ 47 .............. 16 │ 15 ....... 0
┌─────────────────┼──────────────────────┼─────────────┐
│      tag        │        value         │   offset    │
│     16 bit      │        32 bit        │   16 bit    │
└─────────────────┴──────────────────────┴─────────────┘
    區塊標籤             要寫的值           暫存器 offset
```

拿第一筆驗算：

```
u64 = 0x02010000_001b1040
      ├──┘└──────┘└──┘
      │      │      └── offset = 0x1040
      │      └───────── value  = 0x0000001b
      └──────────────── tag    = 0x0201
```

**這個格式 TRM 沒有寫。是實測解出來的。**

## 4. 拿去對 TRM —— 全中

### 結論：`offset` 欄位

把挖到的每個 offset 拿去查 TRM §36.4.2 的暫存器摘要表：

| offset | TRM 給的名字 | 屬於哪個單元 |
|---|---|---|
| `0x100C` | `RKNN_cna_conv_con1` | CNA |
| `0x1010` | `RKNN_cna_conv_con2` | CNA |
| `0x1014` | `RKNN_cna_conv_con3` | CNA |
| `0x1020` | `RKNN_cna_data_size0` | CNA |
| `0x1024` | `RKNN_cna_data_size1` | CNA |
| `0x1028` | `RKNN_cna_data_size2` | CNA |
| `0x1040` | `RKNN_cna_cbuf_con0` | CNA |
| `0x1100` | `RKNN_cna_dcomp_ctrl` | CNA |
| `0x1104` | `RKNN_cna_dcomp_regnu` | CNA |
| `0x4004` | `RKNN_dpu_s_pointer` | DPU |
| `0x5004` | `RKNN_dpu_rdma_s_point` | DPU RDMA |

**一個都沒漏。** 每個 offset 都在 TRM 裡查得到，名字也全部對得上用途。

### 結論：`tag` 欄位

那 16 位元的 tag 一直重複三個值。跟 offset 排在一起看：

| tag | 對應的 offset 範圍 | TRM §36.4.1 位址表說那是誰 |
|---|---|---|
| `0x0201` | `0x1xxx` | **CNA** |
| `0x1001` | `0x4xxx` | **DPU** |
| `0x2001` | `0x5xxx` | **DPU_RDMA** |

**完全吻合。** tag 就是「這筆要寫給哪個單元」的選擇器。

（[ch01](./ch01_hardware.md) §3 那張位址表在這裡派上用場了。）

> ⚠️ tag 的低位元組固定是 `0x01`，高位元組才在變（`02` / `10` / `20`）。
> 這個 `0x01` 是什麼意思，**程式碼和 TRM 都沒說。標為待查。**

## 5. ★ 實驗 5.3：從暫存器讀出整個神經網路

### 結論

TRM §36.4.3 給了 `RKNN_cna_data_size0`（`0x1020`）的位元定義：

```
Bit    Attr  Reset Value   Description
31:27  RO    0x00          reserved
26:16  RW    0x000         datain_width      輸入特徵資料寬
15:11  RO                  reserved
10:0   RW    0x000         datain_height     輸入特徵資料高
```

還有 `RKNN_cna_data_size1`（`0x1024`）：

```
29:16  RW    datain_channel_real    「實際通道數」
15:0   RW    datain_channel         「通道數。int8 模式下必須是 8 的倍數」
```

**有了這把尺，就能把 120 個 task 的 regcmd 全部掃過，把每一層的形狀讀出來。**

`rkspy.c` 做的就是這件事。

### MobileNet v1 的完整架構，從暫存器讀出來

```
  task  op_idx  regcfg    width height       ch  ch_real
  0     1       126         224     99       16        2
  1     1       126         224     99       16        2
  2     1       64          224     28       16        2
  3     2       126         112    100       32       31
  4     2       126         112     14       32       31
  5     3       126         112    100       32       31
  ...
  21    13      126          14     14      256      255
  22    14      126          14     14      512      511
  ...（op 14~24 全部是 14×14×512）
  33    25      126           7      7      512      511
  34    26      126           7      7     1024     1023
  ...
  37    29      126           1      1     1024     1023
  47    31      108           1      1     1008     1000
```

**把 width 那一欄豎著讀：**

```
224 → 112 → 56 → 28 → 14 → 7 → 1
```

**這就是 MobileNet v1。** 每次尺寸減半（stride=2 的卷積），
最後 `1×1×1024` 是全域平均池化，再接分類層。

通道數同步變大：`3 → 32 → 64 → 128 → 256 → 512 → 1024`。
標準的「空間變小、通道變多」。

### `ch_real` 這一欄破了一個案

看這幾組數字：

| op | `ch`（padding 後） | `ch_real` |
|---|---|---|
| 1 | 16 | **2** |
| 2 | 32 | 31 |
| 4 | 64 | 63 |
| 7 | 128 | 127 |
| 31 | 1008 | **1000** |

除了第一層，全部都是 **`ch_real = ch − 1`**。

第一層特別奇怪：padding 後 16，real 卻是 2。

**如果這個欄位存的是「真正的通道數減 1」：**

- op1：`2 + 1 = 3` = **RGB 三通道** ✅
- op31：`1000 + 1 = 1001` = **1001 個分類** ✅

而 demo 印出來的輸出張量正是：

```
index=0, name=MobilenetV1/Predictions/Reshape_1, dims=[1, 1001, 0, 0]
```

**1001。對上了。** 而且 `1001` 進位到 8 的倍數就是 `1008` ——
正好是 `ch` 那一欄，也符合 TRM 說的「int8 模式必須是 8 的倍數」。

兩個獨立的證據（RGB=3、分類數=1001）都指向同一個結論。

> ⚠️ 但 **TRM 明明白白寫的是 `Real channel number`（實際通道數），沒有「減 1」**。
> 實測值一致地少 1。
> **這是 TRM 與實機的落差，我把它記進落差表，不改寫 TRM 的說法。**

## 6. ★ 實驗 5.2：換一個模型，384 KB 的鐵律

### 結論

一個模型不夠。換 **YOLOv5s（640×640）** 再跑一次，看什麼變、什麼不變。

為了不受範例程式綁定的圖片尺寸限制，寫了一個最小的通用執行器：
[`experiments/exp05_run.c`](./experiments/exp05_run.c) ——
載入任何 `.rknn`、餵全 0 的輸入、跑一次就結束。

```bash
$ sudo env LD_PRELOAD=./rkspy.so ./exp05_run .../yolov5s-640-640.rknn
模型: .../yolov5s-640-640.rknn
輸入 1 個、輸出 3 個
  input[0] dims=[1, 640, 640, 3]  size=1228800  fmt=NHWC  type=INT8
rknn_run -> 0
```

第一層的形狀表：

```
  task  op_idx  regcfg    width height       ch  ch_real
  0     1       126         640     34       16        2
  1     1       126         640     34       16        2
  2     1       61          640     34       16        2
  ...（一路到 task 17，全部 640×34）
  18    1       64          640     28       16        2
```

**寬度從 224 變成 640。** 通道還是 16/`ch_real`=2（一樣是 RGB）。

但最有意思的是：**MobileNet 的第一層切成 3 條，YOLOv5s 切成 19 條。**

### 為什麼切？384 KB。

TRM §36.1 的規格表寫著：

> ⚫ **384KBx3 internal buffer**

每顆核心只有 384 KB 內部緩衝。整張特徵圖塞不下，就得**切成橫條分批算**。

把每一條的大小算出來（`寬 × 高 × 通道`）：

| 層 | W | H | ch | 大小 | 佔 384 KB |
|---|---|---|---|---|---|
| MobileNet op1 | 224 | 99 | 16 | 354,816 | **90.2%** |
| MobileNet op2 | 112 | 100 | 32 | 358,400 | **91.1%** |
| MobileNet op4 | 112 | 49 | 64 | 351,232 | **89.3%** |
| MobileNet op7 | 56 | 50 | 128 | 358,400 | **91.1%** |
| **YOLOv5s op1** | **640** | **34** | **16** | **348,160** | **88.5%** |

**兩個不同的模型、五個不同的層，全部落在 88~91%。**
op2 和 op7 甚至是**同一個數字** `358,400`。

再看**沒有被切開**的層：

| 層 | W | H | ch | 大小 | 佔 384 KB |
|---|---|---|---|---|---|
| MobileNet op10 | 28 | 28 | 256 | 200,704 | 51.0% |
| MobileNet op14 | 14 | 14 | 512 | 100,352 | 25.5% |
| MobileNet op26 | 7 | 7 | 1024 | 50,176 | 12.8% |

**全部在一半以下，所以一條就吃得下，不用切。**

> **模型編譯器（RKNN Toolkit）在挑分條高度時，target 就是「剛好塞進 384 KB」。**
>
> 這是 TRM 的一行規格，透過暫存器值，在兩個模型上被驗證出來。

至於為什麼是 88~91% 而不是 99% —— 剩下那 ~34 KB 大概是留給權重或雙緩衝的。
**這句是我的推測，程式碼和 TRM 都沒說。**

## 7. 我不知道的部分

**這一節是刻意寫的。** 一份誠實的教材要說清楚邊界在哪。

### ① 分條高度加起來，對不上

| 模型 | 第一層分條高度 | 加總 | 輸入高 | 差 |
|---|---|---|---|---|
| MobileNet v1 | 99 + 99 + 28 | **226** | 224 | **+2** |
| YOLOv5s | 34 × 18 + 28 | **640** | 640 | **0** |

同一顆硬體、同一個欄位，**行為不一樣**。

MobileNet 多出的 2 列，很容易想成「卷積接縫要重疊」——
但如果是那樣，YOLOv5s 也該多出來（它第一層的卷積核更大），實際卻剛好 640。

**我沒有能站得住的解釋。標為待查，不猜一個聽起來合理的說法。**

> 想追下去的話，方向是：拿更多模型跑一輪，看「+0」和「+2」跟什麼相關
> （卷積核大小？padding？stride？）。這是讀者可以自己做的延伸實驗。

### ② `tag` 的低位元組固定是 `0x01`

`0x0201` / `0x1001` / `0x2001`，高位元組是區塊選擇器（已驗證），
**低位元組永遠是 `0x01`。是什麼，不知道。**

### ③ regcmd 的其他欄位

我們只解讀了 `0x1020` 和 `0x1024`（因為 TRM 有位元定義）。
每個 task 有 **126 筆**設定，其他 120 幾筆是什麼，
TRM §36.4.3 裡都查得到，但這章沒有一一展開。

**這不是「不知道」，是「沒寫」。** 讀者可以照同一個方法自己查。

### ④ `librknnrt.so` 怎麼決定切法

我們看得到**結果**（分條高度），看不到**決策過程**。
那在閉源的模型編譯器裡。

從 ioctl 只能反推「它做了什麼」，不能反推「它怎麼想的」。

## TRM 與實機對不上的地方（累積）

| # | 章 | TRM 怎麼說 | 實機／程式碼 | 判斷 |
|---|---|---|---|---|
| 1 | ch01 | 暫存器表沒有 `0x0000` / `0x0004` | 有，`0x0000` = `"FIRE"` | TRM 漏寫 |
| 2 | ch01 | 位址表說 GLOBAL 是 `0xf000~0xf004` | 同章摘要表卻有 `0xF008` | TRM 自己矛盾 |
| 3 | ch01 | `0x0020` bit31 = RO / reset 0 | 讀到 `1` | 不明，待查 |
| 4 | ch01/02/04 | 完全沒提 `rockchip,iommu-v2` | 實測確認它在做 IOVA 翻譯 | TRM 沒收錄 |
| 5 | ch02 | §36.5.2 只提 AHB / AXI 兩個時脈域 | 另有 `clk_npu`、`pclk` | 合理，非錯誤 |
| 6 | ch04 | 沒提 IOMMU domain | `MAX_IOMMU_DOMAIN_NUM = 16`，使用者可指定 | 待查 |
| 7 | **ch05** | 完全沒有 `regcmd` 的格式定義 | 實測解出：8 bytes = tag(16) + value(32) + offset(16) | **TRM 沒收錄**。這是驅動／韌體介面，不算硬體暫存器 |
| 8 | **ch05** | `0x1024` 的欄位叫 `datain_channel_real`（實際通道數） | 實測值一致地比實際通道數**少 1**（RGB 讀到 2、1001 類讀到 1000） | **TRM 描述不精確**。應為 `N−1` 編碼 |
| 9 | **ch05** | — | regcmd 的 `tag` 低位元組固定 `0x01`，意義不明 | 待查 |

## 本章結論一句話

> **AI 模型被編譯成一串 8 位元組的指令，每一筆說「往哪個單元的哪個暫存器寫什麼值」。**
>
> 驅動不懂模型，只把清單的位址交給硬體。
> NPU 的 Register File Fetch Unit 自己去 DRAM 讀，自己照著設定 CNA / DPU / PPU。
>
> 而那些值不是亂數 —— 從 `RKNN_cna_data_size0` 裡讀得出
> `224 → 112 → 56 → 28 → 14 → 7 → 1`，
> **整個神經網路的形狀，白紙黑字寫在暫存器裡。**
>
> 分條的高度也不是隨便挑的：兩個模型、五個層，
> 每一條都剛好是 **384 KB 內部緩衝的 88~91%**。
