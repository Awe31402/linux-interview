# 04　DDR 頻率：頻寬跟著頻率走，但預設策略會讓「延遲敏感」的程式吃虧

> 實驗日期：2026-09-26　工具：`tools/membw.c`、`tools/dmc_bw.sh`

## 一句話結論

- 記憶體頻寬幾乎和 DDR 頻率成正比：528 MHz → 8 GB/s，2112 MHz → 28 GB/s。
- 預設的 `dmc_ondemand` 只看「頻寬用了幾成」。像指標追逐這種**一次只讀一點、但每次都要等**的程式，
  用量很低 → DDR 一直停在 528 MHz → **延遲 245 ns，比最高速的 129 ns 慢 1.9 倍**。

---

## 1. 平常 DDR 在哪個頻率

```
$ cat /sys/class/devfreq/dmc/trans_stat
     From  :   To
           :  528000000 1068000000 1560000000 2112000000   time(ms)
* 528000000:         0         0         0         4   2684916
 1068000000:         2         0         0         0      1270
 1560000000:         1         0         0         0        53
 2112000000:         2         2         1         0       223
Total transition : 12
```

開機 45 分鐘（期間還跑了好幾輪 CPU 滿載）：**99.9% 的時間在 528 MHz**，只切了 12 次。
CPU 的 NEON 加熱器不碰記憶體，所以不會拉高 DDR。

## 2. dmc_ondemand 怎麼決定頻率

`drivers/devfreq/rockchip_dmc.c:2754` `devfreq_dmc_ondemand_func()`，每 50 ms（`.polling_ms = 50`）：

- 用 DFI（DDR 介面監控）算 `busy_time / total_time` = 頻寬使用率
- 使用率 > `upthreshold`（**40%**）→ 直接跳最高
- 介於 20%~40% → 維持
- 更低 → 按比例往下算，但不低於 `auto_min_rate`

sysfs 可調：`/sys/class/devfreq/dmc/upthreshold`（40）、`downdifferential`（20）。

開機訊息裡另外有幾個「情境頻率」，例如 `video_4k_rate = 1560000000`、`hdmirx_rate = 2112000000`、
`boost_rate = 2112000000`，是給特定場景（播 4K、HDMI-in、觸控加速）用的。

## 3. 實驗：把 DDR 釘在每個頻率量一次

`dmc_bw.sh`：沒有 `userspace` governor（可選的只有 `rknpu_ondemand dmc_ondemand simple_ondemand`），
改用 `min_freq = max_freq = X` 把 DDR 釘住。每種情況跑：

- **1T**：綁 cpu4（A76），256 MB 緩衝區，memset 寫 / 讀 / memcpy，取 5 次最佳；再跑 256 MB 隨機指標追逐量延遲
- **4T**：綁 cpu4-7（4 顆 A76），每執行緒 128 MB

同時每 50 ms 記一次 `dmc/cur_freq`。

| DDR | 1T 寫 | 1T 讀 | 1T 複製 | **延遲** | 4T 寫 | 4T 讀 | 4T 複製 |
|-----|------|------|--------|---------|------|------|--------|
| 528 MHz | 7.80 | 7.58 | 7.53 | **247.3 ns** | 8.21 | 8.13 | 7.55 |
| 1068 MHz | 15.56 | 12.97 | 13.51 | 172.7 ns | 16.30 | 16.17 | 15.23 |
| 1560 MHz | 22.30 | 16.17 | 18.53 | 145.4 ns | 23.76 | 23.20 | 20.12 |
| 2112 MHz | 26.93 | 18.21 | 22.61 | **128.7 ns** | 28.61 | 27.86 | 25.00 |
| **dmc_ondemand（預設）** | 27.28 | 18.44 | 21.00 | **244.7 ns** | 28.65 | 27.96 | 24.95 |

（頻寬單位 GB/s；複製算「讀 + 寫」兩份）

預設模式下 DDR 頻率分佈（每 50 ms 一次，共 142 筆）：**528 MHz 118 筆**、1068 × 4、1560 × 2、2112 × 18。

## 4. 解讀

**頻寬測試：預設策略沒問題。** memset/memcpy 一跑起來 DFI 使用率馬上破 40%，50 ms 內跳到 2112 MHz，
取 5 次最佳值時已經是全速，所以和「釘在 2112」一樣。

**延遲測試：預設策略吃虧 1.9 倍。** 指標追逐每次只拿 64 bytes 就得等下一個位址，
頻寬用量極低（< 1 GB/s），DFI 看起來「很閒」，DDR 就留在 528 MHz。
但這種程式恰好是**延遲**決定速度，而 DDR 頻率越低延遲越高：

```
528 MHz  247 ns
1068     173
1560     145
2112     129
```

會受影響的真實工作：資料庫索引、鏈結串列/樹狀結構走訪、編譯器、直譯器……

## 5. 頻寬離理論值多遠

若 DDR 匯流排是 64-bit（RK3588 常見 4 × 16-bit LPDDR4x/5 通道；**這台實際的 DRAM 類型沒去查**），
2112 MHz 的理論值 = 2112 × 2 × 8 B = 33.8 GB/s。4 執行緒讀 27.9 GB/s ≈ **82%**。
528 MHz 理論 8.45 GB/s，實測 8.13 ≈ **96%**（頻率低時控制器比較容易餵滿）。

單執行緒讀（18.2 GB/s）比寫（26.9）低很多：單顆 A76 能同時發出的讀取 miss 有限，
讀要等資料回來；寫（memset）可以一路丟出去。

## 6. 建議

| 情境 | 做法 |
|------|------|
| 延遲敏感的伺服器/編譯工作 | `echo 1560000000 > /sys/class/devfreq/dmc/min_freq`（或 2112000000） |
| 想省電 | 維持預設 |

也可以試著調低 `upthreshold`，但指標追逐的使用率本來就很低，調門檻幫助有限，**沒測**。
